위키는 별도 사이트가 아니라 repo 안에 마크다운으로 살아요. AGENTS.md와 CLAUDE.md에는 이 폴더의 목차만 들어가서, LLM이 필요한 문서를 찾아 들어가요.

PR을 올리면
날짜를 대신 확인해줘요

유효기간을 적어두기만 하면 아무도 안 봐요. 그래서 GitHub Actions에 검사를 붙였어요. 문서를 건드린 PR에서 기한이 지난 문서를 찾아내요.

name: docs-lint

on:
  pull_request:
    paths:
      - "AGENTS.md"
      - "docs/**"
      - "scripts/docs-lint.mjs"
      - ".github/workflows/docs-lint.yml"
  push:
    branches: [main, release]
    paths:
      - "AGENTS.md"
      - "docs/**"
      - "scripts/docs-lint.mjs"
      - ".github/workflows/docs-lint.yml"

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version-file: ".nvmrc"
      - name: Run docs lint
        run: node scripts/docs-lint.mjs --strict

문서가 낡으면 사람이 아니라 CI가 먼저 알려줘요.

위키가 더 크게 앞섰어요

Tencent WeChat 팀이 문서를 링크 달린 위키 페이지로 컴파일하고, 에이전트가 검색·읽기·링크 따라가기를 반복하는 LLM-Wiki를 만들어 RAG 7종과 비교했어요. 답변 모델은 전부 같게 뒀어요.

MuSiQue (2~4홉 질문) F1위키 0.739 · Dense RAG 0.611
2WikiMultiHopQA F1위키 0.911 · Dense RAG 0.815
HotpotQA (2홉) F1위키 0.839 · Dense RAG 0.764
가장 강한 기존 방식(LightRAG)보다도 +2.0~8.1 F14홉 질문에선 F1 0.983질문당 지연 시간은 RAG와 비슷 (평균 2.5~3.9쪽만 읽어요)

단순히 더 많은 텍스트를 가져온 게 아니에요. 중간에 발견한 단서로 다음 검색을 이어갈 수 있는 구조가 차이를 만들었어요.

위키 구조보다 중요한 건
"쓰기 전에 얼마나 읽느냐"였어요

구성 요소를 하나씩 빼봤어요. 위키 구조를 없애도 F1이 6~7점 떨어지지만, 에이전트가 한 번만 검색하고 링크를 안 따라가게 하면 12~14점이 떨어졌어요. 구조는 순회할 때만 힘을 발휘해요.

단계적 순회를 뺐을 때 (MuSiQue F1)0.739 → 0.601, −13.8
위키 구조를 뺐을 때0.739 → 0.669, −7.0
Error Book(자기 수정)을 뺐을 때0.739 → 0.699, −4.0

우리 위키에 그대로 적용되는 교훈

AGENTS.md는 목차만, 진짜 내용은 docs/에서 읽게인덱스 → 페이지 → 링크를 따라 들어가는 순회가 성능의 핵심이에요. 그리고 문서 오류의 절반 이상이 "깨진 링크"라서, 우리도 docs-lint처럼 자동 검사가 필요해요.

다른 연구에선 비용이
21배 든다는 결과도 있어요

같은 달 나온 사전등록 비교 연구예요. 논문 24편에 질문 13개로 벡터 RAG와 위키를 붙였는데, 종합력은 위키가 크게 앞섰지만 질문당 토큰은 21배, 응답 시간은 6.6배였어요. 한 줄짜리 사실 찾기는 RAG가 동등 이상이었어요.

🧩
문서 사이 연결 종합력
10점 만점에 위키 9.5 vs RAG 5.4. 인용이 주장을 실제로 뒷받침한 비율도 40% vs 19%로 위키가 높았어요.
🪙
질문당 토큰 21배
에이전트가 페이지를 여러 번 읽어서요. "미리 만들어두면 질문은 싸진다"는 가설은 이 실험에선 뒤집혔어요.
🔍
단순 사실 찾기는 RAG
Tencent 연구에서도 단일 문서 질문은 HippoRAG 2가 2.3점 더 높았어요. 두 연구가 같은 방향이에요.
✂️
질문을 쪼갠 RAG가 따라와요
하위 질문으로 분해한 RAG는 종합력 격차의 88%를 좁혔어요. 다만 인용 정확도 격차는 남았어요.

쓰는 방법은 두 가지예요

지금 같이 보거나, 남겨두고 나중에 보거나. 뷰어는 둘 다 같은 화면이에요.

📡
라이브 디버깅
SDK ↔ Relay ↔ 뷰어를 실시간으로 중계해요. 저장하지 않고, 서버 메모리 링버퍼만 써요. 공유 링크를 보내면 상대 화면의 개발자도구가 내 브라우저에 떠요.
⏺️
기록 & 재생
사용자가 "기록"을 누른 순간부터 CDP 스트림을 PostgreSQL(메타) + S3(청크)에 영구 저장해요. 나중에 DevTools 재생(Network·Console)이나 화면 재생(rrweb)으로 다시 봐요.

기록엔 뷰어가 없어서 응답 body, 쿠키·스토리지 스냅샷을 SDK가 따로 실어 보내요.

AI와 일하며 배운 네 가지

네 프로젝트와 논문, 다른 팀 사례까지 돌아보니 결국 같은 네 문장으로 모여요.

🤝
모르는 것부터 맡기고, 아는 것은 검토해요
ElevenLabs 연동, Next.js MSW 설정, Go 웹소켓 릴레이처럼 내가 헤맬 영역에서 위임 효율이 가장 컸어요. 반대로 내가 잘 아는 영역은 AI가 쓴 걸 검토하는 쪽이 빨랐어요. "무엇을 맡길까"의 기준은 난이도가 아니라 나와의 거리였어요.
→ vetify.ai · Bugted
📝
규칙은 말로 하지 않고 파일과 코드에 심어요
CLAUDE.md의 Mock 동기화 지침, frontmatter의 reviewed·ttl_days, PR마다 도는 docs-lint, 담당자 라우팅 표 routing/*.json. 프롬프트로 부탁한 규칙은 잊히지만, 파일과 CI에 심은 규칙은 매번 지켜져요. 지식 팩토리의 메타 루프도 같은 말이에요. 반복된 지적은 규칙으로 승격하세요.
→ vetify.ai · LLM Wiki · Bugted · 지식 팩토리
🎯
AI가 판단하는 자리를 하나로 좁혀요
Relay는 메시지를 읽지 않고 흘려보내요. 교열은 파이썬 규칙이고, 판단하는 AI는 데스크 한 자리예요. 담당자는 자동 배정이 아니라 추천이고, 제보자가 확인해요. 자율성은 최대로 올리되, 사람 검토 없이 통과시키는 범위는 신뢰가 쌓인 만큼만 넓혀요. 어디서 AI가 판단하고 어디서 판단하지 않을지 정하는 게 설계예요.
→ Bugted · 지식 팩토리
🔗
맥락은 자산이지만 유통기한이 있어요
소스코드가 원본이고 위키가 맥락이에요. 위키의 product-owners.md는 Bugted의 담당자 추천이 됐고, 버그 기록 한 건은 다이제스트 한 장이 되어 에이전트에게 닿아요. 산출물은 다음 프로젝트의 재료가 돼요. 다만 맥락은 코드보다 빨리 낡아요. 그래서 만드는 비용은 맥미니 러너 같은 인프라로, 낡는 문제는 유효기간과 주기 갱신으로 풀어야 해요.
→ LLM Wiki · Bugted
